<p><strong>한 문장:</strong> 공장이 우리 회사 상황을 넣으면 감축제품을 도입했을 때 얼마나 줄고 얼마를 아끼는지를 <strong>공식 근거와 함께</strong> 보여줌. 설치 뒤에는 같은 기준으로 실제 감축량을 측정해 비교함.</p>

            └──────────────┬─────────────────────────┬────────────┘
                           │                         │
          ┌────────────────▼──────────┐   ┌──────────▼────────────────┐

<li><code>site</code>, <code>asset</code>, <code>meter</code>, <code>sensor</code>, <code>tag</code></li>
<li><code>telemetry_raw</code> → <code>telemetry_validated</code></li>
<li><code>production</code>, <code>operation</code>, <code>weather</code></li>
<li><code>baseline_model</code>(승인 후 잠금·버전), <code>calculation_run</code>, <code>savings_result</code></li>
<li><code>ghg_result</code>, <code>approval</code>, <code>audit_log</code>, <code>evidence_file</code>(해시)</li>
<li>모든 측정값에 <code>data_origin</code></li>
</ul>
</li>
<li><code>emission_factor</code>는 위 <code>FactorSet</code>/<code>Factor</code>로 통합함.</li>
<li><strong>예상과 실측을 잇는 고리:</strong> <code>InstalledProduct</code>(productId, siteId, assetId, 설치일, 템플릿 version, <strong>고객이 가져온 1단계 스냅샷 파일</strong>)<ul>
<li>1단계에는 서버 저장이 없음. 그래서 고객이 내보낸 입력·결과 파일(F8)을 2단계에서 올리면 그 스냅샷과 실측을 비교해 달성률을 계산함.</li>
</ul>
</li>
</ul>
<h3>7-5. 1단계 저장 방식</h3>
<ul>
<li><strong>기준데이터와 제품 데이터는 저장소의 JSON 파일로 관리함.</strong> 변경 이력은 Git이 남기고, 반영 전에 사람이 변경 내용을 검토함.</li>
<li><strong>커밋할 때마다 자동 검사를 돌림</strong> (GitHub Actions)<ul>
<li>JSON 형식 검사: 필수 필드, 단위, sourceId 존재 여부</li>
<li>원문 파일 경로가 실제로 있는지 확인</li>
<li>세트별 GWP 일치 검사</li>
<li>합산 검산값과 테스트 벡터 확인</li>
<li>금지 문구 검사</li>
</ul>
</li>
<li>서버 DB는 2단계(로그인·저장·MRV)에서 PostgreSQL로 도입함.</li>
</ul>
<h2>8. 계산·판정 엔진</h2>
<h3>8-1. 계산 흐름</h3>
<pre><code>1. 입력 정규화   단위 변환(발열량 판본·총/순 기준 지정), 필수값·범위 검사, 기본값 표시
2. 적용 조건     템플릿 적용 조건 확인 (예: 스팀트랩 시험 압력 범위). 벗어나면 &quot;계산 불가 + 사유&quot;
3. 에너지 절감   산식 템플릿 → 연간 절감량. 0 이하면 &quot;절감 없음&quot;으로 멈춤
4. 탄소 환산     절감량 × 계수(성분별 × GWP) → tCO2eq
5. 경제성        연간 절감액 = 절감량 × 단가 − 연간 유지관리비(선택 입력)
                 단순 회수기간[년] = 도입비 ÷ 연간 순절감액 (순절감액 ≤ 0 → &quot;회수 불가&quot;)
6. 인정 판정     인정 규칙 × (제품 + 고객 입력) → 판정 + 부족 조건
7. 스냅샷        입력·버전·제품값 사본·커밋 해시 → 결과 해시
</code></pre>
<ul>
<li>엔진은 화면·저장소와 분리된 순수 TypeScript 함수로 만듦. 같은 입력이면 항상 같은 결과가 나와야 함.</li>
<li>계산 중간에는 반올림하지 않고 표시할 때만 반올림함.</li>
<li>비용은 연료비(또는 전기요금)만 셈. 스팀 생산비 같은 겹치는 비용 항목은 더하지 않음.</li>
</ul>

<h2>9. MRV 연계 설계 (2단계 준비)</h2>
<ul>
<li><strong>측정 항목:</strong> 산식 템플릿에 MRV 측정 항목과 최소 기간을 포함함(02 문서 4장).<ul>
<li>압축기: 15분 전력, 기준선 30일 이상, 보고 1년</li>
<li>스팀트랩: AM0017 모니터링 방법론. 트랩 조사를 분기 25% 또는 연 1회 100% 실시하고, 스팀 생산량·온도·압력과 보일러 효율은 월 단위로 측정. 실측 감축 = 기준선 손실 − 조사에서 발견된 고장 트랩 손실</li>
</ul>
</li>
<li><strong>IPMVP 옵션:</strong> 제품 단위 감축은 옵션 A·B로 산정함. 옵션 C(사업장 전체) 결과를 제품별로 나눠 배분하지 않음.</li>
<li><strong>판정 체계:</strong> 상위 3단계 &quot;정상 / 확인 필요 / 오류&quot; 아래에 상세 코드 7종(VALID·MISSING·OUTLIER·ESTIMATED·MANUAL·SYNTHETIC·INVALID)을 연결함. 이상치는 자동 삭제하지 않음.</li>
<li><strong>업무 상태:</strong> 계산중 → 품질확인 → 검토 → 승인 → (외부 검증의견 첨부). &quot;검증완료&quot;라는 상태명은 쓰지 않음.</li>
<li><strong>모델 통계 기준:</strong> 공단 M&amp;V 가이드라인 4.0을 따름. R² ≥ 0.75, t ≥ 2, CV &lt; 20%이고, 절감량이 기준선 불확도의 2배 이상이어야 인정함. 내부 명세에서 비어 있던 기준값을 이것으로 채움.</li>
</ul>
