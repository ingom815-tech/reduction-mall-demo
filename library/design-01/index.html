1. 무엇을 만드나

한 문장: 공장이 우리 회사 상황을 넣으면 감축제품을 도입했을 때 얼마나 줄고 얼마를 아끼는지를 공식 근거와 함께 보여줌. 설치 뒤에는 같은 기준으로 실제 감축량을 측정해 비교함.

  • 사업기획 PPT 21장 차별성("같은 제품 데이터로 추천·계산·판매·MRV를 잇는다")을 이 구조로 구현함.

2. 설계 원칙

# 원칙 근거
1 모든 숫자에 근거를 붙인다. 결과마다 산식 버전, 계수 세트 버전, 제품 성능값, 입력값, 출처 ID, 데이터 커밋 해시를 스냅샷으로 남김 PPT 21·22장, 내부 MRV 명세(감사로그·해시 봉인)
2 계수는 용도별 세트로, 성분별로 저장한다. 전력 계수는 CO2·CH4·N2O를 따로 저장하고 합산은 엔진이 함. 세트 안의 GWP 기준이 다르면 오류로 멈춤 계수가 문서마다 넷(0.4173 / 0.4544 / 0.4567 / 0.4747)이고 성분·GWP 기준이 다름
3 발열량 기준을 단계별로 고정한다. 보일러 효율 계산에는 총발열량을, 배출량 계산에는 순발열량을 씀 LNG 총·순 차이 약 11%
4 기준 데이터는 연도·버전으로 추가하고 덮어쓰지 않는다 배출계수 1년 주기, 고시 개정(2025.10), K-택소노미 개정(2025.12)
5 "예상"·"실측"·"검증의견 첨부"를 구분한다. 플랫폼의 품질 점검은 제3자 검증이 아님 삼양 질의답변, SmartEcoCity v6
6 인정 판정은 정해진 결과값만 쓴다. 해당 가능 / 조건 충족 시 가능 / 해당 없음 / 제도 시행 전. 부족한 조건 목록을 함께 표시하고, 샘플 제품에는 판정을 표시하지 않음 PPT 22장 리스크 06
7 원본은 바꾸지 않는다. 원천 → 정제 → 계산 → 승인 단계를 분리하고 이력을 남김 내부 MRV 명세, 마리나체인 요청서
8 AI는 돕기만 한다. AI는 읽고 제안하며, 규칙 엔진이 계산하고, 담당자가 승인하고, 검증기관이 확인함 ABC 제안서, 마리나체인 요청서
9 단위와 기본값을 숨기지 않는다. 단위는 반드시 고르게 하고, 근거 없는 기본값은 두지 않음. 기본값을 쓰면 결과에 표시함 중기부 엑셀 1,000배 오류 위험, 설명용 가정값(전기 150원)의 오남용 위험

3. 1단계 범위

3-1. 만드는 것

# 기능 설명
F1 제품 카탈로그 갤러리 대표 이미지 카드 4열(한 화면 16개). 카테고리 메뉴: 지원사업 4유형(에너지 절감형·공정 최적화형·배출 진단형·신재생 에너지형) + 기타. 필터: 감축 자원(전력·연료·스팀)
F2 제품 상세 표준 레이아웃(6장). 성능 수치마다 근거 문서와 근거 등급 표시
F3 회사 상황 입력 공통 항목 + 제품군별 항목. 근거 있는 기본값만 제공
F4 장바구니 시뮬레이션 제품별 결과와 합계. 같은 에너지 흐름의 대체재는 함께 담지 못함
F5 계산 가능 제품 목록 회사 상황으로 계산할 수 있는 제품을 예상 감축량 순으로 정렬. 업종 기반 추천은 2단계
F6 근거 보기 숫자마다 산식, 계수(성분·GWP·연도·출처), 입력값 구분(고객 입력/기본값), 인정 판정과 부족 조건
F7 기준데이터 레지스트리 출처대장, 계수 세트, 발열량, 단가, 산식 템플릿, 인정 규칙, 표현 규칙
F8 입력·결과 파일 회사 상황 입력을 파일로 내보내고 다시 불러오기. 결과 PDF에 근거 각주, 버전, 데이터 커밋 해시 포함
F9 문의와 고지 결과 화면의 문의 버튼(외부 문의 폼 링크), 면책 고지, 이용약관

3-2. 1단계에서 하지 않는 것 (나중 목록)

  • 로그인, 서버 저장, 견적·주문·설치 관리
  • MRV 실측 (데이터 구조는 미리 맞춰 둠)
  • 지원금·보조율 시나리오, 지원사업용 계수 세트 적용
  • 업종→공정 매핑 기반 추천, AI 추천
  • 관리자 화면 (1단계는 저장소 파일로 관리)
  • 홈페이지 주소 업종 분석, 녹색금융 연계, 결제
  • 상류·하류 관계 제품 조합 계산(예: 스팀트랩 + 보일러 교체)

4. 첫 제품군 (추천안)

순위 제품군 제품 이유 한계
1 스팀트랩 영인 PHV-R(Steamsaver), O-TRAP(SUS Technoworks) 영인 실제 제품. 연료(Scope 1) 감축. 공식 방법론 AM0017 원문으로 계산함(고객 스팀트랩 조사 결과 기반) 고객의 스팀트랩 조사(진단) 결과가 있어야 계산됨. 자체 화석연료 보일러 고객만 해당. 1년차 예상은 제품과 무관하게 같고, 제품별 차이는 설치 후 조사로 확인됨. 제조사 시험은 자체 시험이라 표시만 함
2 공기압축기 (인버터) 샘플 제품 (참고자료 동산공업 규격서 사양 참고) 국내 공식 산식이 가장 잘 갖춰짐(2024 설비별 가이드라인, 공단 산정tool). 효율관리기자재 최저효율, K-택소노미 붙임9 "인버터제어형 압축기"와 연결됨 실제 파트너 제품이 없어 "샘플" 표시. 예상 산식은 공단 tool 수식 이식(R2) 후 확정
3 (조건부) 실외기 차광 영인 슈퍼네트(WSE) 고객 입력이 단순함(냉방 전력) 성적서 없음. 결과를 "현장 사례 범위"로만 표시
카탈로그만 차열도료, 쿨루프, ECO-Almag 영인 제품 상세 페이지·자료실 제공 계산 불가 사유를 표시
  • 스팀트랩으로 영인 실제 제품과 공식 방법론(AM0017) 기반 연료 계산을, 압축기로 국내 공식 산식·공식 Tool과의 일치를 검증함. 연료와 전력 두 축이 모두 확인됨.
  • 현실적인 제약: 1단계에서 계산이 되는 제품은 스팀트랩 2종과 샘플 압축기 정도임. 그래서 추천보다 "제품을 깊게 보여주고 정확히 계산하는 것"에 집중함.
  • 스팀트랩 입력의 특징: 고객은 스팀트랩 조사표(고장 유형, 용도, 오리피스 지름, 압력, 개수, 운전시간)를 입력함. 조사 결과가 없는 고객에게는 "스팀트랩 진단 후 계산 가능"으로 안내하고 문의로 연결함(진단 서비스가 영업 접점이 됨).

  • 할당대상업체 결과 화면: 기본 결과(국가 계수)와 "제4차 할당계획에 쓰인 계수(참고)" 결과를 다른 영역에 나눠 표시하고, 두 값을 한 합계에 섞지 않음.

7. 데이터 구조

7-4. MRV 확장 (2단계)

  • 내부 MRV 명세 v1.0의 객체를 그대로 씀.
    • site, asset, meter, sensor, tag
    • telemetry_raw → telemetry_validated
    • production, operation, weather
    • baseline_model(승인 후 잠금·버전), calculation_run, savings_result
    • ghg_result, approval, audit_log, evidence_file(해시)
    • 모든 측정값에 data_origin
  • emission_factor는 위 FactorSet/Factor로 통합함.
  • 예상과 실측을 잇는 고리: InstalledProduct(productId, siteId, assetId, 설치일, 템플릿 version, 고객이 가져온 1단계 스냅샷 파일)
    • 1단계에는 서버 저장이 없음. 그래서 고객이 내보낸 입력·결과 파일(F8)을 2단계에서 올리면 그 스냅샷과 실측을 비교해 달성률을 계산함.

7-5. 1단계 저장 방식

  • 기준데이터와 제품 데이터는 저장소의 JSON 파일로 관리함. 변경 이력은 Git이 남기고, 반영 전에 사람이 변경 내용을 검토함.
  • 커밋할 때마다 자동 검사를 돌림 (GitHub Actions)
    • JSON 형식 검사: 필수 필드, 단위, sourceId 존재 여부
    • 원문 파일 경로가 실제로 있는지 확인
    • 세트별 GWP 일치 검사
    • 합산 검산값과 테스트 벡터 확인
    • 금지 문구 검사
  • 서버 DB는 2단계(로그인·저장·MRV)에서 PostgreSQL로 도입함.

8. 계산·판정 엔진

8-1. 계산 흐름

1. 입력 정규화   단위 변환(발열량 판본·총/순 기준 지정), 필수값·범위 검사, 기본값 표시
2. 적용 조건     템플릿 적용 조건 확인 (예: 스팀트랩 시험 압력 범위). 벗어나면 "계산 불가 + 사유"
3. 에너지 절감   산식 템플릿 → 연간 절감량. 0 이하면 "절감 없음"으로 멈춤
4. 탄소 환산     절감량 × 계수(성분별 × GWP) → tCO2eq
5. 경제성        연간 절감액 = 절감량 × 단가 − 연간 유지관리비(선택 입력)
                 단순 회수기간[년] = 도입비 ÷ 연간 순절감액 (순절감액 ≤ 0 → "회수 불가")
6. 인정 판정     인정 규칙 × (제품 + 고객 입력) → 판정 + 부족 조건
7. 스냅샷        입력·버전·제품값 사본·커밋 해시 → 결과 해시
  • 엔진은 화면·저장소와 분리된 순수 TypeScript 함수로 만듦. 같은 입력이면 항상 같은 결과가 나와야 함.
  • 계산 중간에는 반올림하지 않고 표시할 때만 반올림함.
  • 비용은 연료비(또는 전기요금)만 셈. 스팀 생산비 같은 겹치는 비용 항목은 더하지 않음.

8-2. 계수 세트 선택 (1단계)

고객 결과 기본 함께 표시
일반 기업 FS-KR-NATIONAL-2023 (전력 0.4173, AR5) "국가 공표 최신 계수(2023년도) 기준"
할당대상업체 같음 별도 영역에 "제4차 할당계획에 쓰인 계수(참고, 0.4544)" 결과. 근거 [추정] 표시
지원사업 신청 목적 2단계 —
  • 지원사업 세트(2단계)는 해당 공고 Tool과 같은 결과를 내도록 별도로 계산함(공고 Tool의 정수 내림 등 포함).

8-3. 장바구니 규칙

  • 제품군마다 에너지 흐름 키가 있음.
  • **같은 키는 기본이 "택1"**임. 같은 설비를 대체하는 제품은 함께 담을 수 없고, 담으려 하면 이유를 안내함.
  • 다른 키는 합산함. 1단계 제품군(스팀트랩·압축기·실외기)은 서로 겹치지 않음.
  • 순차 적용(같은 흐름에 보완 제품을 겹쳐 적용)과 상류·하류 관계는 2단계에서 정의함. 순차 적용은 기준 에너지량을 입력으로 받는 산식에만 허용함.

8-4. 계산 가능 제품 목록 (F5)

  1. 고객 입력으로 계산이 가능한 제품만 순위에 넣음.
  2. 정렬은 연간 예상 감축량(tCO2eq) 순, 동률이면 회수기간 순.
  3. 근거 등급을 함께 표시함. 점수는 깎지 않고 투명하게 보여줌.

9. MRV 연계 설계 (2단계 준비)

  • 측정 항목: 산식 템플릿에 MRV 측정 항목과 최소 기간을 포함함(02 문서 4장).
    • 압축기: 15분 전력, 기준선 30일 이상, 보고 1년
    • 스팀트랩: AM0017 모니터링 방법론. 트랩 조사를 분기 25% 또는 연 1회 100% 실시하고, 스팀 생산량·온도·압력과 보일러 효율은 월 단위로 측정. 실측 감축 = 기준선 손실 − 조사에서 발견된 고장 트랩 손실
  • IPMVP 옵션: 제품 단위 감축은 옵션 A·B로 산정함. 옵션 C(사업장 전체) 결과를 제품별로 나눠 배분하지 않음.
  • 판정 체계: 상위 3단계 "정상 / 확인 필요 / 오류" 아래에 상세 코드 7종(VALID·MISSING·OUTLIER·ESTIMATED·MANUAL·SYNTHETIC·INVALID)을 연결함. 이상치는 자동 삭제하지 않음.
  • 업무 상태: 계산중 → 품질확인 → 검토 → 승인 → (외부 검증의견 첨부). "검증완료"라는 상태명은 쓰지 않음.
  • 모델 통계 기준: 공단 M&V 가이드라인 4.0을 따름. R² ≥ 0.75, t ≥ 2, CV < 20%이고, 절감량이 기준선 불확도의 2배 이상이어야 인정함. 내부 명세에서 비어 있던 기준값을 이것으로 채움.

10. 기술·운영

항목 1단계 추천 이유
화면 Next.js + TypeScript, 정적 사이트로 빌드 서버가 필요 없음. 비용이 낮고 운영 부담이 작음
계산 위치 브라우저에서 계산 (엔진이 순수 TS) 공장 에너지 사용량이 서버로 전송되지 않음. 서버 로그나 해외 서버 문제가 생기지 않음
데이터 저장소 JSON → 빌드 시 공개용 데이터만 포함 비공개 성적서, 홍보 사용 불가 수치, 내부 메모 필드는 빌드에서 제외함
공식 원문 사이트에는 원본 기관 URL 링크만 둠 387건을 재배포하지 않음(저작권·최신본 문제)
고객 안내 "입력값은 이 브라우저에서만 계산에 쓰이며 저장되지 않습니다" 실제 동작과 같은 정확한 문구
사용 통계 개인·기업 정보를 남기지 않는 익명 페이지 통계만 사용(선택) 어떤 제품이 많이 보이는지 파악
배포 정적 호스팅(예: Cloudflare Pages, GitHub Pages, Vercel 유료 요금제), 예산 알림 설정 상업 이용 조건은 요금제마다 다르므로 선택 전 확인 필요(Vercel 무료 요금제는 상업 이용 제한으로 알려져 있음, [미확인])
시험 엔진 단위 테스트 + 검산 테스트 + 공식 자료 대조 테스트 (12장 P1) 숫자 오류가 가장 비싼 실패임
2단계 PostgreSQL, 로그인(기존 인증 서비스 연동), 시계열 저장(15분 데이터), 국내 리전 결과 저장·MRV가 필요해지는 시점

단계 만들 것 완료 기준
P0 기준데이터 JSON(출처대장, 계수 세트 2종, 발열량, 단가, 인정 규칙, 표현 규칙) + JSON 형식 정의 + 자동 검사(GitHub Actions) 모든 값에 sourceId가 있음. 원문 경로가 존재함. 세트별 GWP 일치. 합산 검산값 일치(0.4173, 0.4544)
P1 계산 엔진 + 템플릿 2종 + 테스트 아래 대조 범위 통과. 음수·0 절감과 단위 오류를 막는 테스트 포함
P2 제품 데이터(PHV-R, O-TRAP, 압축기 샘플, 카탈로그 제품) + UI-01 갤러리 + UI-02 상세 모든 수치에 출처와 근거 등급. 비공개 자료가 빌드 결과물에 없음
P3 UI-03 입력 + 단일 제품 결과 + UI-06 근거 보기 + F8 입력 파일 입력 검증 3단계 동작. 근거까지 2클릭. 내보낸 파일로 같은 결과가 재현됨
P4 UI-05 장바구니 + UI-04 목록 + F9 문의·고지 같은 흐름 키 제품은 함께 담기지 않음
P5 점검: 금지 문구, 근거 링크, 반응형·접근성, 결과 PDF 점검표 전 항목 통과

P1 대조 범위 (공식 Tool은 계수·GWP·반올림 방식이 달라 탄소량을 직접 비교하지 않음)

  • 압축기: 공단 산정tool과 **에너지 절감량(kWh)**이 같은지 확인함. 사례값(정속 37/26 kW, Loading 70% → 20.9%)을 재현해야 함.

  • 탄소 환산: 테스트 전용 세트(SAR, 0.4567)로 경매 Tool과 같은 값이 나오는지 확인함. 운영 세트에는 쓰지 않음.

  • 스팀트랩: 공식 Tool이 없으므로 Steam Table 엔탈피 값(공단 보일러 tool)과 수기 계산 3건으로 대조함.

  • 단계마다 커밋하고 다음 단계로 넘어감.

  • 단계별 상세 작업 지시는 결정사항 확정 후 03_제작계획.md로 작성함.

13. 위험과 대응

위험 대응
예상치를 보장으로 오인 "예상" 라벨, 가정 각주, 회수기간에 지원금·배출권 미포함, 면책 고지
계수·기준 변경을 놓침 출처대장의 "다음 확인일"로 매월 점검 목록을 만듦. 1단계는 담당자가 수동으로 확인하고, 자동화한다면 실패 알림과 담당자를 정함
제조사 자체 시험값의 신뢰 편차 근거 등급·시험 주체·처리 주석 표시. 공급사에 제3자 시험을 요청함(압력별 누설량 등)
스팀트랩 외부사업 인정 부담 AM0017은 비슷한 공장 5곳 비교군 조사를 요구함. 인정 판정에 부족 조건으로 안내하고, 국내 승인 목록 현행 여부(R3 잔여)와 "유지보수" 해당 여부(R9)를 확인함
인정 판정 오안내 조직경계·유지보수 제외·규모별 기한 같은 핵심 조건을 판정 항목에 넣음. 샘플 제품은 판정하지 않음
공식 Tool과 결과 불일치 (2단계 지원사업) 공고 Tool과 같은 계수·산식 세트로 별도 계산
비공개 자료 유출 비공개 파일·필드는 빌드에서 제외. 공식원문은 링크만 둠
비교광고 문제 기존 트랩 시험값(특정 제품 1개)은 화면에 쓰지 않음
